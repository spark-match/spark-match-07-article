\section{Orquestaci\'on y despliegue}

El despliegue se apoya en un enfoque \emph{serverless} sobre AWS e infraestructura
como c\'odigo con Terraform, con dos ambientes (\texttt{dev} y \texttt{prod}) y
automatizaci\'on mediante GitHub Actions.

\subsection{Backend serverless (TypeScript + AWS SAM)}

El backend de plataforma est\'a escrito en \textbf{TypeScript} y sigue un dise\~no
orientado a dominios (DDD). Se despliega como funciones \textbf{AWS Lambda}
orquestadas con \textbf{EventBridge} y empaquetadas con \textbf{AWS SAM}. Este
modelo evita administrar servidores, escala autom\'aticamente con la demanda y
solo factura por invocaci\'on, lo que resulta conveniente para un proyecto
acad\'emico con tr\'afico intermitente.

\begin{lstlisting}[style=bashstyle, caption={Build y despliegue del backend con AWS SAM}, label={lst:sam-deploy}]
sam build
sam deploy --config-env dev     # ambiente de desarrollo
sam deploy --config-env prod    # ambiente productivo (aprobacion manual)
\end{lstlisting}

\subsection{Agente y motor de scoring (Python)}

El agente conversacional y el motor de scoring se ejecutan en Python. El agente
usa el \emph{harness} \texttt{deepagents} sobre Bedrock (AgentCore) y
\texttt{langmem} para la persistencia del perfil; el motor de scoring opera sobre
\texttt{features.csv} con Pandas/NumPy. Es importante notar que el agente
\textbf{no expone un framework web tradicional} (no usa FastAPI ni Flask): corre
como c\'odigo Python dentro del harness, y la exposici\'on HTTP la provee el
backend \emph{serverless} (API Gateway + Lambda). Estos componentes se integran con
Bedrock para las invocaciones al LLM.

\subsection{Contenerizaci\'on (Docker)}

Aunque el modelo de despliegue es \emph{serverless}, la contenerizaci\'on con
\textbf{Docker} est\'a presente en el ciclo: \texttt{aws sam build} empaqueta las
funciones Lambda como \textbf{im\'agenes de contenedor} (usando Docker localmente
para reproducir el entorno de ejecuci\'on), y el agente se ejecuta como un
\textbf{contenedor gestionado} en Bedrock AgentCore. As\'i se garantiza que el
entorno sea reproducible entre desarrollo y producci\'on sin administrar servidores
ni un orquestador de contenedores propio.

\subsection{Infraestructura como c\'odigo (Terraform)}

La infraestructura se provisiona con \textbf{Terraform}, con m\'odulos separados
por ambiente (\texttt{dev} y \texttt{prod}). Se emplea \textbf{AWS Budgets} como
control de costos. Entre los recursos: funciones Lambda y reglas de EventBridge
del backend, base de datos \textbf{RDS PostgreSQL}, almacenamiento en S3 para
snapshots del dataset, e IAM con privilegios m\'inimos. La calidad de la
infraestructura se refuerza con escaneo de seguridad (\emph{checkov}) y
\emph{linting} de Terraform (\emph{tflint}).

\subsection{CI/CD con GitHub Actions}

El c\'odigo se organiza en la organizaci\'on de GitHub \texttt{spark-match}, con
repositorios separados por dominio. \textbf{GitHub Actions} ejecuta las pruebas
autom\'aticas y las validaciones de infraestructura en cada cambio, siguiendo la
estrategia de ramas del equipo (rama de integraci\'on \texttt{dev} y promoci\'on
a \texttt{prod}).

Adem\'as, el pipeline de CI incorpora an\'alisis est\'atico de c\'odigo:
\textbf{SonarCloud} (\emph{quality gate}) detecta \emph{code smells}, bugs
potenciales y duplicaci\'on, mientras que \textbf{CodeQL} (GitHub) realiza el
escaneo de seguridad (\emph{SAST}) para identificar vulnerabilidades en el
c\'odigo antes del \emph{merge}. Junto con \emph{checkov} y \emph{tflint} en la
infraestructura, esto conforma un control de calidad y seguridad automatizado que
refuerza las buenas pr\'acticas de MLOps y DevOps del proyecto.

\begin{lstlisting}[style=yamlstyle, caption={Workflow de CI (ejemplo simplificado)}, label={lst:gh-actions}]
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: "3.12"}
      - run: pip install -r requirements.txt
      - run: pytest
  infra:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: tflint --recursive
      - run: checkov -d infra/
\end{lstlisting}

\subsection{Escalabilidad}

El sistema \textbf{no utiliza Kubernetes}: la escalabilidad se apoya en servicios
\emph{serverless} autoadministrados de AWS. El backend (AWS Lambda + API Gateway) y
el agente (Bedrock AgentCore) escalan autom\'aticamente seg\'un la demanda, sin
administrar servidores ni cl\'usteres. Esto ofrece una escalabilidad adecuada para
el alcance del proyecto, con l\'imites conocidos: AWS Lambda admite \textbf{100
ejecuciones concurrentes} en cuentas gratuitas (\textbf{1000} en cuentas de pago),
ampliables bajo solicitud. Para cargas de millones de usuarios simult\'aneos se
requerir\'ia una arquitectura orientada a contenedores (p.ej.\ Kubernetes/EKS); en
este proyecto, \textbf{AgentCore y Lambda cumplen una funci\'on equivalente}
---orquestaci\'on y escalado autom\'atico--- sin el costo operativo de administrar
un cl\'uster. Se trata, por tanto, de una escalabilidad \emph{media} suficiente
para la demostraci\'on.

\subsection{Despliegue en la nube (AWS)}

El entorno productivo se aloja en AWS. La estrategia de dos ambientes
(\texttt{dev} y \texttt{prod}) permite validar cambios antes de promoverlos a
producci\'on, y \textbf{AWS Budgets} vigila el gasto mensual. Los costos exactos
de operaci\'on y la URL de demo se documentar\'an tras el despliegue final.
