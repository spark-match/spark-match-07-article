\section{Orquestaci\'on y despliegue}

El despliegue se apoya en un enfoque \emph{serverless} sobre AWS e infraestructura
como c\'odigo con Terraform, con dos ambientes (\texttt{dev} y \texttt{prod}) y
automatizaci\'on mediante GitHub Actions.

\subsection{Backend serverless (TypeScript + AWS SAM)}

El backend de plataforma est\'a escrito en \textbf{TypeScript} y sigue un dise\~no
orientado a dominios (DDD). Se despliega como funciones \textbf{AWS Lambda}
orquestadas con \textbf{EventBridge} y empaquetadas con \textbf{AWS SAM}. Este
modelo evita administrar servidores, escala autom\'aticamente con la demanda y
solo factura por invocaci\'on, lo que resulta conveniente para un proyecto
acad\'emico con tr\'afico intermitente.

\begin{lstlisting}[style=bashstyle, caption={Build y despliegue del backend con AWS SAM}, label={lst:sam-deploy}]
sam build
sam deploy --config-env dev     # ambiente de desarrollo
sam deploy --config-env prod    # ambiente productivo (aprobacion manual)
\end{lstlisting}

\subsection{Agente y motor de scoring (Python)}

El agente conversacional y el motor de scoring se ejecutan en Python. A
diferencia de lo planeado originalmente, el agente \textbf{s\'i expone un
framework web tradicional}: \texttt{src/api/app.py} monta una aplicaci\'on
\textbf{FastAPI}, servida con \textbf{uvicorn}, con un endpoint
\texttt{/ag-ui} que responde en \emph{streaming} (Server-Sent Events) y un
endpoint \texttt{/health} para el \emph{health check} del balanceador. El
agente usa el \emph{harness} \texttt{deepagents} y \texttt{langmem} para la
persistencia del perfil (ver Secci\'on~\ref{sec:implementation}); Bedrock se
usa \'unicamente como pasarela de inferencia del LLM (invocaciones a Claude),
no como plataforma de hospedaje del contenedor. El motor de scoring, por su
parte, opera sobre \texttt{features.csv} con Pandas/NumPy, aunque a\'un no
est\'a conectado end-to-end con el agente (ver
Secci\'on~\ref{sec:results}).

\subsection{Contenerizaci\'on (Docker)}

El uso de \textbf{Docker} no es sim\'etrico entre los dos servicios del
proyecto. El backend serverless \textbf{no se empaqueta como imagen de
contenedor}: \texttt{aws sam build} usa \texttt{BuildMethod: esbuild} por
funci\'on, que compila y empaqueta cada Lambda de TypeScript como un
\textbf{artefacto ZIP} (Node.js~24.x). El agente conversacional, en cambio,
\textbf{s\'i se conteneriza}: su \texttt{Dockerfile} (\emph{multi-stage},
\texttt{uv} para resolver dependencias + \texttt{python:3.14-slim} para el
\emph{runtime}, usuario no-\emph{root}, plataforma \texttt{linux/arm64}) se
construye en CI, se publica en \textbf{Amazon ECR} y se despliega como una
\textbf{tarea de Amazon ECS Fargate} (Graviton/ARM64) detr\'as de un
\emph{Application Load Balancer}, con \textbf{CloudFront} delante para
terminar TLS. La raz\'on documentada en el m\'odulo de Terraform para elegir
ECS Fargate en vez de Bedrock AgentCore Runtime es que el agente necesita
conexi\'on TCP directa a RDS para el \emph{checkpointer}/\emph{store} de
LangGraph y \emph{streaming} SSE de larga duraci\'on en \texttt{/ag-ui}, algo
que AgentCore Runtime no garantiza y que un \emph{timeout} fijo de 30s en
API Gateway (HTTP API) cortar\'ia; el ALB permite un \emph{idle timeout}
configurable de hasta 4000s. As\'i, la contenerizaci\'on con Docker
garantiza que el entorno del agente sea reproducible entre desarrollo y
producci\'on \textbf{con} un orquestador de contenedores propio (ECS), no
sin \'el.

\subsection{Infraestructura como c\'odigo (Terraform)}

La infraestructura se provisiona con \textbf{Terraform}, con m\'odulos separados
por ambiente (\texttt{dev} y \texttt{prod}). Se emplea \textbf{AWS Budgets} como
control de costos. Entre los recursos: funciones Lambda y reglas de EventBridge
del backend; el \textbf{cl\'uster ECS Fargate}, el ALB, la distribuci\'on
CloudFront y el repositorio \textbf{ECR} del agente conversacional
(\texttt{modules/agent-service}); la base de datos \textbf{RDS PostgreSQL}
compartida por ambos servicios; almacenamiento en S3 para \emph{snapshots} del
dataset; e IAM con privilegios m\'inimos (roles de ejecuci\'on y de tarea
separados para el agente). La calidad de la infraestructura se refuerza con
escaneo de seguridad (\emph{checkov}) y \emph{linting} de Terraform
(\emph{tflint}).

\subsection{CI/CD con GitHub Actions}

El c\'odigo se organiza en la organizaci\'on de GitHub \texttt{spark-match}, con
repositorios separados por dominio. \textbf{GitHub Actions} ejecuta las pruebas
autom\'aticas y las validaciones de infraestructura en cada cambio, siguiendo la
estrategia de ramas del equipo (rama de integraci\'on \texttt{dev} y promoci\'on
a \texttt{prod}).

Adem\'as, el pipeline de CI incorpora an\'alisis est\'atico de c\'odigo:
\textbf{SonarCloud} (\emph{quality gate}) detecta \emph{code smells}, bugs
potenciales y duplicaci\'on, mientras que \textbf{CodeQL} (GitHub) realiza el
escaneo de seguridad (\emph{SAST}) para identificar vulnerabilidades en el
c\'odigo antes del \emph{merge}. Junto con \emph{checkov} y \emph{tflint} en la
infraestructura, esto conforma un control de calidad y seguridad automatizado que
refuerza las buenas pr\'acticas de MLOps y DevOps del proyecto.

\begin{lstlisting}[style=yamlstyle, caption={Workflow de CI (ejemplo simplificado)}, label={lst:gh-actions}]
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: "3.12"}
      - run: pip install -r requirements.txt
      - run: pytest
  infra:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: tflint --recursive
      - run: checkov -d infra/
\end{lstlisting}

\subsection{Escalabilidad}

El sistema \textbf{no utiliza Kubernetes}. El backend escala de forma
autom\'atica y sin administrar servidores (AWS Lambda + API Gateway), con
l\'imites conocidos: AWS Lambda admite \textbf{100 ejecuciones concurrentes}
en cuentas gratuitas (\textbf{1000} en cuentas de pago), ampliables bajo
solicitud. El agente, en cambio, corre en \textbf{ECS Fargate}, que s\'i es un
orquestador de contenedores administrado: hoy el servicio se despliega con un
\texttt{desired\_count} \textbf{fijo} (sin \emph{autoscaling} configurado
todav\'ia --- el m\'odulo de Terraform deja el campo preparado con
\texttt{lifecycle.ignore\_changes} para cuando se agregue), por lo que la
capacidad del agente es constante y no reactiva a la demanda; s\'i cuenta con
un \emph{deployment circuit breaker} que revierte autom\'aticamente un
despliegue fallido a la revisi\'on anterior. Para cargas de millones de
usuarios simult\'aneos se requerir\'ia habilitar \emph{autoscaling} en el
servicio ECS (o migrar a una arquitectura Kubernetes/EKS); en el alcance
actual del proyecto esto se documenta como trabajo pendiente, no como una
funci\'on ya activa. Se trata, por tanto, de una escalabilidad \emph{media}
suficiente para la demostraci\'on, con el backend escalando autom\'aticamente
y el agente con capacidad fija.

\subsection{Despliegue en la nube (AWS)}

El entorno productivo se aloja en AWS. La estrategia de dos ambientes
(\texttt{dev} y \texttt{prod}) permite validar cambios antes de promoverlos a
producci\'on, y \textbf{AWS Budgets} vigila el gasto mensual. Los costos exactos
de operaci\'on y la URL de demo se documentar\'an tras el despliegue final.
